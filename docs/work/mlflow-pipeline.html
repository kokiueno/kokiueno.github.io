An ML pipeline on MLflow

  • AT&S Austria Technologie & Systemtechnik AG
  • Leoben, Austria
  • 2023 – 2024
  • Data Science Intern, Semiconductor R&D

A research team runs a lot of experiments and remembers almost none of them. I built and operated the semiconductor R&D team's ML pipeline on MLflow so that every run left a record behind it — and kept it running as everyday infrastructure, not a one-off setup.

01 What MLflow is

MLflow is an open-source platform for managing the machine learning lifecycle. It started at Databricks and is now developed under the Linux Foundation, released under the Apache 2.0 licence. It is deliberately unopinionated: it does not care which framework you train in, where you run it, or how you deploy — it gives you a common way to record what happened and to hand a model to whoever needs it next.

The problem it solves is mundane and universal. Someone trains a model that works, then changes six things and trains another. Two weeks later nobody can say which combination produced the good number, the notebook has moved on, and the weights are in a folder called final_v3_actually. MLflow makes the record a side effect of running the code rather than something you have to remember to write down.

02 What it gives you

Experiment tracking

Every run records its parameters, its metrics over time, and its output artifacts — plots, weights, confusion matrices, whatever you attach. Runs group into experiments, and the UI sorts and filters across them, so “which settings gave the best score” is a query rather than an archaeology project.

Autologging

One call and MLflow hooks into the training library itself — scikit-learn, PyTorch, TensorFlow, XGBoost and others — capturing parameters, metrics and the model without the researcher instrumenting anything by hand. This is the difference between a tool people adopt and one they route around.

A standard model format

MLflow saves models in “flavors” — a common envelope around a framework-specific model, plus the environment needed to load it. A scikit-learn model and a PyTorch model come back through the same interface, so downstream code does not have to care which one it got.

Model Registry

A named model with numbered versions, each carrying a link back to the run that produced it. Versions move through stages, annotations and approvals ride along, and the question “what exactly is in production right now” has one answer instead of several.

Reproducible runs

MLflow Projects package code together with its environment specification and entry points, so a run can be repeated on another machine months later and land in the same place. Reproducibility stops depending on whether the person who ran it is still on the team.

Serving & evaluation

A registered model can be served behind a REST endpoint or scored in batch straight from the registry, and MLflow's evaluation tooling scores candidates on a shared dataset so comparisons are made on the same footing. Recent versions extend the same tracing idea to LLM and GenAI workloads.

03 What I built and ran

Stood the pipeline up

Built the semiconductor R&D team's ML pipeline on MLflow — tracking wired into the training code, models versioned in the registry, runs reproducible from the recorded environment.

Operated it, not just installed it

Ran it as day-to-day infrastructure for the team rather than handing over a setup and walking away — the part that decides whether an MLOps effort survives contact with a deadline.

Applied to the R&D work

The same pipeline carried the team's modelling work — anomaly detection on manufacturing data, and the prediction models built on PCB simulation output.
